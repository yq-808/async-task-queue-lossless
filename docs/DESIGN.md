# 设计说明

本文回答笔试题里面试会深挖的三件事：**「不丢失」的实现边界**、**容量与背压**、**重试与幂等**，
并说明场景建模、优雅停机和可观测性的做法。每个结论后面都标了对应的代码和验证（测试或脚本）。

---

## 1. 场景与任务模型

### 场景：AI 文档摘要（LLM summarization）

AI 应用里常见的异步任务：用户上传一篇文档，后台调用大模型生成摘要，前端轮询结果。
请求要立刻返回，摘要可以晚几秒到几分钟拿到。

| 项目 | 说明 |
|---|---|
| 任务类型 | `SUMMARIZE`（`TaskHandler` 接口可扩展其它类型，如向量化、翻译） |
| 输入 | `bizKey`（业务幂等键）、`priority`（HIGH / NORMAL / LOW）、`payload`：`text`（≤ 20 万字符）、`documentId`、`maxSummaryChars`、`model` |
| 输出 | `summary`、`inputTokens`、`outputTokens`、`contentSha256`、`modelLatencyMs` |
| 耗时特征 | **IO 等待为主的混合型**：CPU 段（分词 + 指纹计算）约 1–20 ms，与文本长度成正比；IO 段（等模型返回）200–1500 ms。等待/计算 ≈ 50 : 1 |
| 失败概率（模拟） | 8% 模型限流/超时（业务可重试），2% 网关 503（系统可恢复），极少量输入非法（业务不可重试）、代码缺陷（系统不可恢复）。每类都能用 `payload.simulate` 强制触发 |

代码：[`SummarizeTaskHandler`](../src/main/java/io/github/yq808/taskqueue/handler/SummarizeTaskHandler.java)

### 耗时特征如何决定并发模型

- 线程大部分时间在等模型返回，不占 CPU，所以**工作线程数不按 CPU 核数定，而按下游允许的并发定**。
  按 Little 定律 `并发 = 吞吐 × 单次耗时`：想要约 20 个/秒、单次约 0.85 s，需要约 17 个并发。
  模型服务通常按账号给并发配额，默认 16 个线程就是对着这个配额设的（`taskqueue.worker.threads`）。
  如果按 CPU 密集来设（核数 + 1），机器 CPU 几乎闲着，吞吐却只有 IO 型配置的一小部分。
- CPU 段很短，和 IO 段放在同一个线程里做，不值得拆成两个池。如果以后 CPU 段变重（例如本地做 embedding），
  应拆成「CPU 池（核数大小）→ IO 池（配额大小）」两级流水线，避免 CPU 活占着 IO 配额。
- 每次执行有超时（`execution.timeout`，默认 10 s），超时按「业务可重试」处理，防止慢请求把线程耗光。

## 2. 总体结构

```
          POST /api/tasks
                │
     ┌──────────▼───────────┐  ① 校验 → ② 幂等检查 → ③ 准入控制（背压）→ ④ INSERT 提交 → 202
     │ TaskSubmissionService│
     └──────────┬───────────┘
   ④ 提交成功即「接收成功」     ⑤ 快速通道：直接放进内存队列（满了就留在磁盘上）
                │                          │
        ┌───────▼────────┐        ┌────────▼────────────────────────┐
        │  H2（文件模式） │◀──────│  BoundedPriorityBlockingQueue    │
        │  task           │ 补货   │  有界 · 3 级优先级 · 老化防饿死   │
        │  task_result    │ (低水位)│  只存 id + 优先级（磁盘上的索引）  │
        │  task_attempt   │───────▶└────────┬────────────────────────┘
        └───────▲────────┘ TaskDispatcher   │ poll
                │                   ┌───────▼────────┐
                │  claim（CAS+租约）  │  WorkerPool     │ 16 个线程
                └───────────────────│  TaskProcessor  │→ TaskHandler（模拟模型调用）
                  结果/重试/失败      └────────────────┘
                  （带 version 防护）
     维护线程：租约回收 · 积压计数同步 · 吞吐统计 · 过期结果清理
```

分层：`web`（HTTP）→ `engine`（准入、调度、执行、停机）→ `persistence`（状态迁移）→ `queue`（纯并发数据结构，不依赖 Spring）。

### 任务状态机

```
             submit
               │
               ▼        claim          success
          ┌─PENDING──────────▶RUNNING──────────────▶SUCCEEDED
          │    ▲   ▲             │  │  │
          │    │   │  停机中断回写 │  │  │ 业务不可重试
          │    │   └─────────────┘  │  └──────────────▶FAILED ──┐
          │    │  租约过期/崩溃恢复   │ 业务可重试(次数未用完)        │ redrive
          │    └────────────────────┤ 系统可恢复(系统重试未用完)     │
          │                         ▼                             │
          │                     RETRY_WAIT ──(退避到期)──▶ 被 claim  │
          │                         次数用完 / 系统不可恢复          │
          │                         ──────────────────▶DEAD_LETTER─┤
          └──────────────────────────────────────────────────────┘
```

所有状态迁移都是**带条件的 UPDATE**（WHERE 里写明期望的 status 和 version），返回 0 行就说明别人先动了，
当前线程放弃写入。见 [`TaskRepository`](../src/main/java/io/github/yq808/taskqueue/persistence/TaskRepository.java)。

## 3. 「不丢失」的实现边界

### 3.1 核心决定：先落盘，再入内存（write-ahead）

**接收成功的定义：任务行以 `PENDING` 状态 INSERT 并提交成功之后，才返回 202。**
内存队列里只放 `(id, priority)`，它是磁盘数据的一个有界、有序的索引，**任何时刻都不是任务的唯一副本**。

由此得到：

| 故障时刻 | 结果 | 依据 |
|---|---|---|
| INSERT 提交前进程崩溃 | 客户端没收到 202，属于「未接收」；客户端用同一个 `bizKey` 重试即可 | 提交前不承诺 |
| 提交后、202 发出前崩溃 | 任务已在库里；客户端重试拿到 **同一个 taskId**（200, duplicate=true） | 唯一索引 + 载荷哈希 |
| 任务在内存队列里时崩溃 | 内存丢了无所谓，行还是 PENDING，重启后补货线程重新装载 | write-ahead |
| 任务执行中崩溃 | 行停在 RUNNING；重启时被恢复为 PENDING 重新执行 | 启动恢复 + 租约 |
| 执行完、结果提交前崩溃 | 同上，任务会**再执行一次**（至少一次语义） | 见 3.3 |
| 优雅停机 | 正在跑的任务限时完成；超时的被中断并回写为 PENDING，且不计入尝试次数 | 见第 6 节 |

**实测**（`scripts/crash-test.sh`，见 [VALIDATION.md](VALIDATION.md)）：32 个客户端并发提交 8000 个任务，提交还在进行中的第 2 秒 `kill -9`。
崩溃前拿到 202 的 5583 个任务重启后 **0 丢失**；崩溃时正在执行的 15 个被恢复；客户端把 8000 个请求全部重试一遍，
其中 5605 个返回原 taskId——比收到 202 的多 22 个，正是「已提交但 202 没来得及发出」的那部分，重试后照样拿回原任务，
没有丢、也没有重复建任务。最终 8000 个业务键对应 8000 个任务，全部执行完毕。

### 3.2 持久化本身的边界：进程崩溃 vs 机器掉电

H2 文件模式默认 `WRITE_DELAY=500ms`：提交后最多 500 ms 才写进文件，这期间进程被 `kill -9` 会丢掉「已经回了 202」的任务。
所以连接串里设了 **`WRITE_DELAY=0`**：每次提交立刻写入文件（进入操作系统页缓存）后才返回。

- **进程崩溃（OOM、kill -9、JVM 崩溃）：不丢。** 数据已经在操作系统缓存里，进程死了操作系统仍会把它写到磁盘。上面的 kill -9 测试验证的就是这一层。
- **机器掉电 / 操作系统崩溃：最后一小段提交可能丢。** H2 不对每次提交做 fsync。这是选 H2 带来的边界，也是吞吐上的取舍：
  每次提交都 fsync，单机提交速率会从几千次/秒降到磁盘 fsync 能力（普通 SSD 几百到几千次/秒）。
  要把这个窗口也关掉，需要换成支持同步提交的数据库（如 PostgreSQL `synchronous_commit=on`）或者做多副本复制，不在本题范围。
- `DB_CLOSE_ON_EXIT=FALSE`：不让 H2 自己的 JVM 关闭钩子抢先关库，保证停机回写时数据库还能用，由 Spring 在最后关闭。

### 3.3 执行语义：至少一次，靠幂等收敛成「效果上恰好一次」

「结果已算出、还没提交」时崩溃，无法区分「做了没提交」和「没做」，这是任何不依赖分布式事务的系统都绕不开的。
本项目的选择是**至少一次执行 + 处理幂等**：

- 结果和 `SUCCEEDED` 状态在**同一个事务**里提交，库里不会出现「成功但没结果」或「有结果但不是成功」。
- `task_result` 以 `task_id` 为主键，同一任务最多一条结果。
- 处理器拿到 `taskId`，对外部有副作用的调用（比如计费、写别的系统）应该带上它作为幂等键（见 `TaskHandler` 注释）。
- 正常运行（不崩溃）下是**恰好一次**：并发测试 1000 个任务、handler 调用次数正好 1000（`ConcurrencyIntegrationTest`）。

### 3.4 防止「旧工人」覆盖新结果：租约 + 版本号防护

一个工作线程卡住超过租约（默认 60 s，必须大于执行超时 10 s），租约回收线程会把任务交给别人。
如果卡住的线程后来又醒了并试图写结果：每次 claim 都会让 `version + 1`，所有后续写入都带 `WHERE version = ?`，
旧线程的写入影响 0 行，被丢弃并计入 `fencedOut`。见 `TaskStoreTest.aWorkerThatLostItsLeaseCannotWriteItsOutcome`。

### 3.5 毒丸任务

如果某个任务每次都把进程搞崩，它会一直停在 RUNNING、一直被恢复。恢复时**丢失的那次执行也计入尝试次数**，
次数用完的直接进死信（`LEASE_EXPIRED`），不会无限拖垮进程。

## 4. 容量与背压

### 4.1 两层容量：内存队列很小，持久化积压才是真正要限的

| 层 | 默认值 | 作用 | 超限时 |
|---|---|---|---|
| 内存队列 | `线程数 × 8 = 128` | 给工作线程的预取缓冲，保证线程拿任务不用等数据库 | 留在磁盘上（spill），由补货线程以后装载 |
| 持久化积压（PENDING + RETRY_WAIT） | 上限 10000，自适应 | 承诺「接收了就会处理」的总量 | **拒绝：429 + Retry-After** |

**溢出之后怎么回来**：补货线程在两种情况下从库里装载：内存降到低水位；或者刚有一个比内存里最不紧急的任务**更紧急**的任务被挤到了磁盘
（例如内存全是 HIGH 时又来一个 HIGH，之后空位被新来的 LOW 占了）。后一种情况会立刻唤醒补货线程，补货也用 `offerOrEvict`，
所以溢出的 HIGH 会把内存里的 LOW 挤回磁盘，不会排在新来的 LOW 后面。验证：`TaskDispatcherTest`。

**内存队列为什么只要 128**：它只需要盖住「补货间隔」里的消耗。吞吐约 19 个/秒、补货检查间隔 200 ms，
理论上 4 个格子就够；低水位 64 意味着还有约 3 秒的余量时才去补货，补货查询很少。
再大不会提高吞吐，只会让更多任务的顺序在内存里「固定」得更早。
按「线程池大小 × 队列系数」静态配置，系数 8 可调（`queue.capacity-factor`），也可以直接设 `queue.capacity`，
运行时也能改（`setCapacity`，缩容不丢元素）。

**积压上限为什么自适应**：调用方能接受的是「排队等多久」，不是「排第几个」。按 Little 定律
`积压上限 = 吞吐 × 可接受的最大排队时间`（默认 10 分钟），吞吐用每秒完成数的指数滑动平均（EWMA）。
下游变慢时吞吐下降，上限自动收紧，新任务被拒绝而不是被接收后等一小时。
上下限 `[1000, 10000]`：下限防止冷启动或短暂抖动时误拒，上限保护 H2 表规模。没有吞吐样本时用上限。

### 4.2 背压策略选型

| 策略 | 用不用 | 理由 |
|---|---|---|
| 阻塞生产者（offer 带超时） | 队列支持，HTTP 入口**不用** | 会占住 Tomcat 线程，违背「提交接口必须快速返回」 |
| **拒绝 + Retry-After（429）** | **用（主策略）** | 立刻告诉客户端「现在别发」和「多久后再试」；客户端用同一 `bizKey` 重试是幂等的，不会重复建任务 |
| **按优先级分级卸载** | **用** | 积压到上限的 70% 先拒 LOW，90% 拒 NORMAL，100% 才拒 HIGH，高优先级任务始终有余量 |
| **溢出到磁盘（spill）** | **用（内存层）** | 内存满不等于系统满。更紧急的任务可以把内存里最新、最不紧急的那个挤回磁盘（`offerOrEvict`），它在库里还是 PENDING |
| 丢弃最旧 / 丢弃最新 | 不用 | 与「入队不丢失」冲突 |
| CallerRuns | 不适用 | 在 HTTP 线程里跑 1 秒的模型调用，等于没有异步 |

**Retry-After** = `(当前积压 − 本优先级阈值 + 1) / 吞吐`，限制在 1–300 秒，即「按现在的速度，多久能腾出位置」。

**计数方式**：准入维护一个积压估计值，保证它**任何时刻都不小于**库里真实的等待行数，所以新任务的准入不会让积压超过上限：
- 准入时预占一个名额，计入估计值，同时记为「在途」（INSERT 还没提交，数据库的 COUNT 看不到它）；
- 任务回到等待状态（重试、停机回写、租约回收、人工重投）时立刻加回估计值；
- 任务被取走不立刻扣减，等下次校正，这只会多算；
- 每 500 ms 用数据库 `COUNT` 校正一次：新值 = COUNT + 仍在途的预占 + COUNT 执行期间提交或回到等待的任务（它们可能已经被 COUNT 算进去，重复算只会多算）。

预占、确认、校正共用一把很小的锁，所以校正不会覆盖掉它执行期间发生的预占
（`AdmissionControllerTest`：1000 个并发请求、上限 100，准入正好 100 个；校正时不丢在途预占）。
已经接收的任务重试时不会被拒（它们已经被承诺处理），因此积压可以因为重试暂时高于上限，这时新请求会更早被拒。
第一版的校正直接用 COUNT 覆盖估计值，会漏掉在途的预占，上限可能被超出几个；这是代码审查发现后修正的。

**实测**（`scripts/load-test.sh`，上限 800，64 个客户端约 1500 请求/秒）：接收 897、拒绝 4103（全部 429 带 Retry-After）；
HIGH 只占请求量的 20% 却被接收了 359 个，LOW 占 40% 只接收 211 个；内存队列峰值正好 128，659 个任务溢出到磁盘，最终 897 个全部完成。

### 4.3 优先级与防饿死

- 三级优先级，每级一个 FIFO 双端队列，取任务时从高到低。
- **内存里的老化**：低优先级队头等待超过 30 s（`queue.aging-threshold`），就排到新来的高优先级前面。
- **磁盘上的老化**：内存里的老化只帮得到已经在内存里的任务。持续有 HIGH 时，被挤到磁盘上的 LOW 可能永远进不了内存。
  所以每次补货先查出「可运行已超过老化阈值」的非 HIGH 任务（最多容量的 1/8），按最高级别放进内存，然后才按 `priority, next_run_at` 装载其余任务。
  这一点是代码审查发现、修正后用测试证明的：`StarvationIntegrationTest` 在内存 4 格、单工人、持续 44 个 HIGH 的情况下，
  修正前那个 LOW 排在全部 HIGH 之后，修正后它在等过阈值后就被执行，之后还有至少 10 个 HIGH 才开始。
- 验证：`BoundedPriorityBlockingQueueTest`（顺序、老化、逐出规则）、`TaskDispatcherTest`（补货规则）、`PriorityOrderIntegrationTest`（单工人时 3 HIGH → 3 NORMAL → 3 LOW 的实际开始顺序）、`StarvationIntegrationTest`。

### 4.4 自己实现的有界优先级阻塞队列

JDK 的 `PriorityBlockingQueue` 是无界的，不能产生背压，所以基于 `ReentrantLock` + 两个 `Condition`（notEmpty / notFull）自己实现了
[`BoundedPriorityBlockingQueue`](../src/main/java/io/github/yq808/taskqueue/queue/BoundedPriorityBlockingQueue.java)：
`offer` / `offer(timeout)` / `offerOrEvict` / `poll(timeout)` / `take` / `drain` / `close` / `setCapacity`，
另外记录峰值，用于证明从未超限。并发测试：8 个生产者 × 5000 + 8 个消费者，容量 32，重复 3 轮，无丢失、无重复、峰值 ≤ 32。

## 5. 失败、重试与幂等

### 5.1 失败分类

| 分类 | 例子 | 处理 | 计入 attempts |
|---|---|---|---|
| 业务·可重试 `BUSINESS_RETRYABLE` | 模型限流 429、调用超时、模型返回无法解析（模型下次可能答得不一样） | 指数退避后重试；用完 `maxAttempts`（默认 4）进**死信** | 是 |
| 业务·不可重试 `BUSINESS_FATAL` | 文档无法解析、参数非法 | 直接 **FAILED** | 是 |
| 系统·可恢复 `SYSTEM_RECOVERABLE` | 网关 503、IO 错误（包括被包装过的，例如 `UncheckedIOException`、HTTP 客户端的资源访问异常：沿 cause 链查找）、数据库瞬时错误 | 退避后重试，**退还本次尝试**，单独计 `systemRetries`（上限 10）；同时计入熔断器 | 否 |
| 系统·不可恢复 `SYSTEM_FATAL` | 代码缺陷（NPE 等）、`Error` | 直接**死信**并打 ERROR 日志，重试只会重复错误 | 是 |

为什么系统故障不占业务次数：下游挂 1 分钟不是任务的错，如果占次数，一次故障就会把大批健康任务送进死信。
但也不能无限重试，所以有单独的上限。分类代码：[`FailureClassifier`](../src/main/java/io/github/yq808/taskqueue/engine/FailureClassifier.java)，
状态处理：[`TaskProcessor`](../src/main/java/io/github/yq808/taskqueue/engine/TaskProcessor.java)。

### 5.2 重试不放大队列压力

1. **退避**：`1s × 2^(n-1)`，上限 60 s，±20% 抖动，避免同一批失败同时回来。
2. **重试等在磁盘上，不占内存队列**：失败任务写成 `RETRY_WAIT` + `next_run_at`，到期前补货查询根本选不到它。
3. **重试计入积压**：`RETRY_WAIT` 算在准入积压里，重试变多时前门自动收紧，新请求拿到 429。这是一个负反馈回路。
4. **熔断**：连续 5 次系统故障，工作线程暂停取任务 5 秒，不把排队任务一个个变成失败和重试。
5. **上限**：业务重试和系统重试都有上限，超过进死信并记录原因。死信可以人工 `POST /api/tasks/{id}/redrive` 重新投递。
6. **每次尝试都有记录**：`task_attempt` 表记录每次执行的结果、错误分类、错误信息、耗时、执行线程，查询加 `?history=true`。

### 5.3 幂等的三个层次

| 层次 | 做法 | 验证 |
|---|---|---|
| 提交 | `biz_key` 唯一索引 + 载荷 SHA-256（键排序后的规范 JSON）。同键同载荷 → 200 + 原 taskId；同键不同载荷 → 409 + 原 taskId。并发同键请求在唯一索引上竞争，输的一方读出赢家的行再按规则回答 | `ConcurrencyIntegrationTest`：1500 个请求含 500 个重复键 → 恰好 1000 个任务 |

## 6. 优雅停机

`TaskEngine` 实现 `SmartLifecycle`，phase 取最大值，所以收到 SIGTERM 后它**先于** Web 服务器停止、**先于**数据源关闭：

1. **关闭准入**：新提交立刻得到 `503 + Retry-After`；查询接口照常可用（Web 服务器还没停）。
2. **停止补货线程**：用标志位 + 唤醒，**不中断**。
3. **停止工作线程（两阶段）**：
   - 不再取新任务，正在执行的给 `await-running`（默认 20 s）自然完成；
   - 仍未完成的，**只中断正在 handler 里的线程**，它们把任务写回 `PENDING`（错误类型 `SHUTDOWN_INTERRUPTED`，退还本次尝试），再给 `await-interrupted`（默认 5 s）。
4. **关闭并清空内存队列**：这些任务本来就是 PENDING（write-ahead），这里逐个核对它们在库里确实处于等待状态，并打印数量。
5. 停止维护线程，打印停机报告。

线程池因此在 `await-running + await-interrupted` 内收敛（Spring 的 `timeout-per-shutdown-phase` 设成 40 s 留出余量）。
还没停下来的线程，它的任务留在 RUNNING，下次启动由恢复逻辑接手，**依然不丢**。

**为什么不用 `shutdownNow()`**：它会中断所有工作线程，而线程可能正在写 H2。中断落在 H2 的文件写操作上，
会让 `FileChannel` 被关闭（`ClosedByInterruptException`），数据库随之不可用，后面的回写全部失败。
所以每个工作线程有一个 [`WorkerSlot`](../src/main/java/io/github/yq808/taskqueue/engine/WorkerSlot.java)：进入 handler、离开 handler、发中断三个动作持有同一把锁，
**中断只可能在 handler 内部发生**，离开 handler 时清掉中断标记再写数据库。补货线程和维护线程同理，只用标志位停止。

**实测**（`scripts/shutdown-test.sh`，`await-running=1s`）：8 个工人、任务 2–6 s，SIGTERM 时 8 个在跑、61 个在内存队列、200+ 在磁盘。
停机期间的提交拿到 503；引擎 1.0 s 停完（等待 1 s 后中断 7 个仍在执行的任务并回写），JVM 共 3.3 s 退出；
重启后 300 个全部成功，`recoveredAfterCrash = 0`（没有任何任务需要走崩溃恢复），每个任务 attempts = 1。

## 8. 取舍与局限

- **单实例假设**：启动时把所有 RUNNING 视为上一个进程遗留。多实例共享一个库时，claim 的 CAS 和 version 防护本身仍然正确，
  但启动恢复要改成只回收租约过期的行（租约回收线程已经这么做），同时 H2 嵌入式文件模式本身也不适合多进程共享。
- **补货是轮询**：200 ms 一次、只在低水位或有更紧急的任务溢出时查询；快速通道让新任务不必等轮询。换成支持 `LISTEN/NOTIFY` 的数据库可以去掉轮询。
- **吞吐上限在数据库写入**：每个任务至少 3 次写（插入、claim、完成）。本机实测约 1500 请求/秒的突发下 p99 提交延迟 227 ms。
- **维护任务分两个线程**：租约回收、积压校正、吞吐统计共用一个线程；过期数据清理单独一个线程，大批量清理不会拖住积压校正（否则估计值只增不减，会误拒新请求）。
  更高吞吐可以批量 claim、或把结果写入异步批量化。
- **掉电窗口**：见 3.2。
- **少量重复入队**：补货查询和工人 claim 之间有极小的竞争窗口，同一 id 可能在内存里出现两次，第二次 claim 失败直接跳过（`claimMisses` 指标），不影响正确性。
- **Java 17 基线**：没有用虚拟线程。用 Java 21 时可以把工作线程换成虚拟线程，并发上限改用 `Semaphore` 按下游配额控制。
