# 与 AI 的关键对话

本项目按题目要求「使用 AI 作答」：由 Claude Code（模型 Claude Opus 5.5）在一次会话中完成建模、编码、测试、真实运行验证和文档。
下面摘录这次会话里起决定作用的对话与过程：开头是我的原话，后面是 AI 的关键决策和它在真实运行中发现并修正的问题，按时间顺序整理（工具调用的原始输出已省略，保留结论和数字）。

## 1. 需求

> **我**：@Java 开发工程师笔试题-异步任务队列-v1.2.pdf
> build the app to score high in this - use real run real validation - use this git commit loop skill - create a public repo to store the result - mind that another AI agent is doing this too - make sure don't clash on same repo

> **AI**：先读题。题目会深挖三点：「不丢失的实现边界」「容量与背压」「重试与幂等」。我的方案：
> - 场景选 AI 文档摘要，IO 等待为主，线程数按下游模型并发配额定，不按 CPU 核数。
> - **先落盘再入内存**：INSERT 提交成功才返回 202，内存队列只放 id，是磁盘数据的有界索引。这样「停机回写」对排队中的任务天然成立，真正需要回写的是正在执行的任务。
> - 内存队列小而有界（线程数 × 8），真正要限的是**持久化积压**；超限时 429 + Retry-After，按优先级分级拒绝，上限按吞吐自适应。
> - 状态迁移全部是带 status + version 条件的 UPDATE，用版本号挡住失去租约的旧工人。
> - 另一个 AI 也在做同一题：仓库名用 `async-task-queue-lossless`，`gh repo create` 在重名时会直接失败，不会覆盖别人的仓库；本地验证用不常见端口 18763，并在启动前检查端口空闲，避免请求打到对方的服务上。

## 2. 环境问题

> **AI**：本机 Maven Central 连不上（TLS 握手失败），公司 Artifactory 需要内网凭据，不适合个人公开项目。改用阿里云公共镜像构建，并把镜像配置作为可选文件放进仓库（`.mvn/aliyun-settings.xml`），方便国内阅卷人。JDK 用 21 运行、以 17 为编译目标，满足「Java 17 及以上」。

## 3. 关键设计讨论

以下三个问题是 AI 在设计时自己提出并回答的，用来预演面试会深挖的点。

> **自问**：停机时为什么不直接 `executor.shutdownNow()`？
>
> **AI**：它会中断所有工作线程。如果中断落在 H2 的文件写操作上，`FileChannel` 会被关闭，数据库随之不可用，后面的回写全部失败——为了「不丢」反而可能丢。所以每个工作线程有一个 `WorkerSlot`：进入 handler、离开 handler、发中断三件事持有同一把锁，中断只会在 handler 里发生，离开 handler 时先清掉中断标记再写库。补货线程和维护线程都只用标志位停止。

> **自问**：H2 文件模式能保证提交后不丢吗？
>
> **AI**：默认不能。H2 的 `WRITE_DELAY` 默认 500 ms，提交后最多半秒才写文件，这期间 `kill -9` 会丢掉已经回过 202 的任务。连接串设 `WRITE_DELAY=0` 后，提交即写入文件（进入操作系统页缓存），进程崩溃不丢；但 H2 不对每次提交 fsync，机器掉电仍可能丢最后一小段。这是选 H2 的边界，在文档里明确写出来，不假装没有。另外设 `DB_CLOSE_ON_EXIT=FALSE`，避免 H2 自己的关闭钩子在回写之前把库关掉。

> **自问**：重试会不会把队列压垮？
>
> **AI**：重试写成 `RETRY_WAIT` + `next_run_at` 留在磁盘，退避到期前补货查询选不到它，不占内存队列；它又计入准入积压，重试多了前门自动收紧；系统故障不占业务重试次数但有单独上限；连续系统故障触发熔断，工人暂停取任务。

## 4. 真实运行中发现并修正的问题

这些问题单元测试没有暴露，是把服务真正跑起来、真正施压之后才看到的。

1. **同一任务被重复入队**（第一次冒烟运行）
   > **AI**：11 次执行出现了 25 次 `claimMisses`。原因：工人从内存队列取出任务时就把 id 从「在内存中」集合里删了，但 claim 还没提交，补货线程这时查库看到它仍是 PENDING，又放进了队列。改成 claim 完成后才删除（`TaskDispatcher.forget`）。修正后 demo 运行 `claimMisses = 0`，压测 1017 次执行只有 8 次（补货查询本身的极小竞争窗口，无害，文档里说明）。

2. **压测没有压到背压**
   > **AI**：第一版压测脚本用 bash + curl，每秒只能发约 46 个请求，积压始终远低于上限，429 一个都没出现——这样的「通过」没有验证任何东西。改写了一个只依赖 JDK 的并发压测客户端 `scripts/LoadGen.java`，约 1150 请求/秒，这才看到 4087 个 429、按优先级的拒绝分布、内存队列打满 128 和 661 个任务溢出到磁盘。

3. **Prometheus 端点在测试里 404**
   > **AI**：Spring Boot 测试默认关闭指标导出，测试类上加 `@AutoConfigureObservability`；真实运行的 jar 不受影响。

4. **停机测试的配置没生效**
   > **AI**：`SpringApplicationBuilder.properties()` 设的是优先级最低的默认属性，被 `it` 配置文件覆盖了（4 个线程而不是 2 个）。改成命令行参数传入。

5. **p95 大于最大值**
   > **AI**：Micrometer 的百分位是直方图估算，demo 里出现了 p95 = 176 ms、max = 172 ms。汇总时把 p95 限制在 max 以内。

## 5. 验证结论（摘自会话）

下面是会话中第一次运行时的数字。仓库里 [`docs/validation/`](validation/) 的日志是最后一次重跑的结果，数字略有不同，结论相同。

> **AI**：
> - `./mvnw verify`：55 个测试全部通过。
> - `kill -9` 测试：4000 个任务提交到一半杀进程，崩溃前拿到 202 的 3674 个重启后 0 丢失；16 个执行中的任务被恢复；客户端全部重试后，3696 个返回原 taskId（比收到 202 的多 22 个——它们已提交但响应没发出去），最终 4000 个业务键对应 4000 个任务，全部成功。
> - SIGTERM 测试：停机期间的提交返回 503；3 s 后中断 2 个仍在执行的任务并回写，61 个内存中的任务核对确认在库里；重启后 300 个全部成功，没有任何任务走崩溃恢复，每个任务只计 1 次尝试。
> - 压测：上限 800 时接收 913、拒绝 4087（全部带 Retry-After），HIGH 请求量是 LOW 的一半，接收数却多 43%；内存队列峰值正好等于容量 128。

## 6. 代码审查循环与修正

> **我**：use this git commit loop skill
>
> **AI**：完成后对分支跑两轮本地审查：先按仓库约定（命名、结构、文档习惯），再查实现正确性。每一轮由一个全新的子代理执行，只提交「有唯一正确改法且构建和测试保持通过」的修改，有疑问的只报告不提交；一轮没有新提交才进入下一类，最后统一推送一次并开 PR。审查结果见 PR 描述。

第一轮结果：约定审查提交了 1 处（用 import 代替写全包名），正确性审查没有提交，但提出了 6 个需要决策的问题，写进了 PR 描述。

> **我**：Yes, fix them
>
> **AI**：逐个修正，每个都先写能复现问题的测试：
> 1. **磁盘上的低优先级任务会饿死**：内存里的老化帮不到还在磁盘上的任务。每次补货先装载可运行超过老化阈值的任务，并放在最高级别。新写的 `StarvationIntegrationTest` 在旧代码上失败（LOW 排在 44 个 HIGH 之后），修正后通过。
> 2. **溢出的 HIGH 会排在新来的 LOW 后面**：有比内存里最不紧急任务更紧急的任务溢出时，立刻唤醒补货，补货也按「挤掉最不紧急的」规则装载（`TaskDispatcherTest`）。
> 3. **准入上限可能被超出几个**：校正时用数据库计数直接覆盖估计值，会漏掉 INSERT 还没提交的预占。改成预占、确认、校正共用一把小锁，校正时把在途预占和计数期间的变化加回去，估计值永远不小于真实积压；文档里原来「不会超收」的说法也改成了准确的描述。
> 4. **清理任务拖住维护线程**：过期数据清理改到单独的线程，停机时在批次之间退出。
> 5. **同一个上下文里 stop 再 start 不工作**：内存队列可以重新打开，工作线程槽位在启动时重置，start/stop 幂等（`EngineRestartIntegrationTest`）。
> 6. **几类异常归错了类**：被包装的 IO 错误沿 cause 链识别为系统可恢复；模型返回无法解析算业务可重试（受最大次数约束），不再按系统故障重试 10 次。
>
> 另外顺手处理了审查里的小问题：测试类改名为 `GracefulShutdownRestartIntegrationTest`、熔断器注释与行为一致、结果接口在清理竞争下返回 404 而不是 500、删掉两个没人调用的方法。
>
> 修正后测试从 55 个增加到 65 个，全部通过；四个真实运行脚本全部重跑，日志和文档里的数字已更新。重跑时发现两个脚本没测到该测的东西，也一并调整：崩溃测试原来 4000 个请求在 kill 之前就发完了，改成 8000 个、第 2 秒 kill，确保杀在提交过程中；停机测试的等待时间从 3 s 改成 1 s，确保一定有执行中的任务被中断并回写。
